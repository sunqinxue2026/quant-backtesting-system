# 阶段验收报告

项目：Python Quantitative Data Processing and Backtesting System

## 第一阶段：环境检查与总体设计

1. **本阶段目标**：确认 Python 3.10+、Git、依赖和测试环境，确定分层架构、数据口径、交易时序、数据库设计和开发计划。
2. **新增或修改的文件**：需求书、`pyproject.toml`、`requirements.txt`、`README.md`。
3. **已实现的功能**：项目采用 `src/quant_system` 分层结构；入口支持 Python 3.10+；数据库连接由 `DATABASE_URL` 注入；测试使用 pytest。
4. **运行过的命令和测试结果**：`python --version`；`.venv\Scripts\python.exe -m pytest`，当前全量测试通过。
5. **核心数据结构、算法和公式**：行情 DataFrame；信号、订单、成交、持仓和账户快照；收益率公式为 `equity[t]/equity[t-1]-1`。
6. **采用该方案的原因**：分层后数据源、策略、回测和持久化职责清晰，适合面试解释和后续替换实现。
7. **可选替代方案**：可改用 Poetry、Pydantic Settings、Alembic 和更完整的领域对象。
8. **性能瓶颈和后续优化方向**：当前以 Pandas 单股票日线为主；大数据量时需要分批读取、数据库批量写入和列式存储。
9. **面试官可能追问的问题及回答思路**：为什么信号与成交分离？因为收盘后信号只能在下一交易日开盘成交，避免未来函数。
10. **尚未完成的内容**：第一版暂不支持实时交易、多资产、分钟线和完整公司行动还原。
11. **下一阶段开始前需要确认的事项**：数据源必须提供来源、日期范围、复权口径和单位说明。

## 第二阶段：CSV 读取和数据清洗

1. **本阶段目标**：读取 CSV，统一字段和类型，识别重复、冲突记录和行情逻辑错误，输出质量报告。
2. **新增或修改的文件**：`src/quant_system/data/loader.py`、`src/quant_system/cleaning/cleaner.py`、`data/test/`、清洗测试。
3. **已实现的功能**：CSV 适配器、DataLoadRequest、来源和单位元数据、股票代码格式化、日期和数值转换、重复记录、冲突重复、OHLC、价格和成交量检查。
4. **运行过的命令和测试结果**：`python -m pytest tests/test_core.py`；清洗和指标测试通过。
5. **核心数据结构、算法和公式**：`MarketData` 保存 frame、source、price_type 和单位；质量报告保存输入、输出、修复、重复、拒绝和人工确认数量。
6. **采用该方案的原因**：数据源接口不依赖策略和回测，后续可接入其他公开数据源。
7. **可选替代方案**：可使用 Pandera、Great Expectations 或 Polars 做数据质量检查。
8. **性能瓶颈和后续优化方向**：当前一次性加载 CSV；大文件应采用 chunksize 和增量清洗。
9. **面试官可能追问的问题及回答思路**：为什么不能统一 fillna(0)？因为价格、成交量和成交额缺失的业务含义不同，填零会制造虚假行情。
10. **尚未完成的内容**：非交易日和异常成交量的外部交易日历校验仍是简化实现。
11. **下一阶段开始前需要确认的事项**：确认 MySQL 连接和实际数据导入批次的命名规则。

## 第三阶段：数据库和数据访问层

1. **本阶段目标**：建立可追溯的行情、策略、任务、订单、成交、快照和结果表，支持事务。
2. **新增或修改的文件**：`src/quant_system/database.py`、`src/quant_system/repository.py`、`database/migrations/001_init.sql`。
3. **已实现的功能**：SQLAlchemy ORM、SQLite 测试、MySQL URL 配置、数据导入批次表、行情复权口径字段、任务和回测结果表。
4. **运行过的命令和测试结果**：SQLite 事务测试通过；表模型可由 `Base.metadata.create_all` 创建。
5. **核心数据结构、算法和公式**：`symbol + trade_date + price_type` 唯一约束；回测结果以 JSON 保存指标快照；批量写入使用 Session 事务。
6. **采用该方案的原因**：SQLAlchemy 兼容 MySQL 和 SQLite，便于本地测试与生产数据库切换。
7. **可选替代方案**：可使用 Alembic 迁移、SQLModel 或原生 SQL 批量导入。
8. **性能瓶颈和后续优化方向**：当前 ORM 批量写入和 JSON 指标适合第一版；大批量行情可使用 LOAD DATA 和分区表。
9. **面试官可能追问的问题及回答思路**：唯一约束如何防止重复行情？用股票、日期和复权口径共同约束，避免不同口径互相覆盖。
10. **尚未完成的内容**：需要真实 MySQL 实例进行一次端到端导入验证，当前自动化测试使用 SQLite。
11. **下一阶段开始前需要确认的事项**：确认目标 MySQL 的账号、数据库和字符集配置。

## 第四阶段：指标和双均线策略

1. **本阶段目标**：计算收益率和技术指标，生成不含未来数据的交叉信号。
2. **新增或修改的文件**：`src/quant_system/indicators/technical.py`、`src/quant_system/strategies/dual_ma.py`、对应测试。
3. **已实现的功能**：日收益率、累计收益率、SMA、EMA、滚动波动率、成交量均线和买卖交叉信号。
4. **运行过的命令和测试结果**：指标、买入信号和卖出信号测试通过。
5. **核心数据结构、算法和公式**：买入为 `short[t] > long[t] and short[t-1] <= long[t-1]`；卖出为反向条件；窗口不足返回缺失值。
6. **采用该方案的原因**：Pandas rolling 和 ewm 向量化，代码短且可手工复核。
7. **可选替代方案**：可使用 NumPy rolling、TA-Lib 或逐日迭代对象。
8. **性能瓶颈和后续优化方向**：多股票重复计算时可按股票分组并缓存指标。
9. **面试官可能追问的问题及回答思路**：如何防止未来函数？信号只读取当日及之前的收盘数据，成交由下一日引擎处理。
10. **尚未完成的内容**：当前只提供双均线策略，尚未加入参数扫描和样本外分析。
11. **下一阶段开始前需要确认的事项**：确认订单数量、费用和持仓规则。

## 第五阶段：回测引擎和账户管理

1. **本阶段目标**：把信号转换为下一交易日订单，按开盘价、滑点和费用更新现金和持仓。
2. **新增或修改的文件**：`src/quant_system/engine/models.py`、`portfolio.py`、`backtest.py`、回测测试。
3. **已实现的功能**：单股票现货做多、交易单位、资金不足、手续费最低值、卖出税费、基点滑点、持仓批次和 T+1 可卖限制、过期订单。
4. **运行过的命令和测试结果**：确定性次日成交、费用、滑点、资金不足和全量 pytest 测试通过。
5. **核心数据结构、算法和公式**：买入价 `open*(1+slippage_bps/10000)`；佣金 `max(gross*rate,min_commission)`；卖出只消费买入日期早于成交日的 FIFO 批次。
6. **采用该方案的原因**：订单、成交、组合分别负责时序、成交事实和资金持仓，便于定位错误。
7. **可选替代方案**：可使用事件驱动撮合器、订单簿模拟或更完整的交易日历。
8. **性能瓶颈和后续优化方向**：当前逐日循环适合日线；分钟线需要事件队列、缓存和更细的成交模型。
9. **面试官可能追问的问题及回答思路**：为什么不能当天收盘成交？因为信号在收盘后才知道，使用当日收盘成交会产生未来函数。
10. **尚未完成的内容**：停牌、涨跌停和历史费率变化仍未建模。
11. **下一阶段开始前需要确认的事项**：确认绩效年化、基准和报告格式。

## 第六阶段：绩效和可视化

1. **本阶段目标**：生成绩效指标、账户净值、回撤、价格信号和基准对比报告。
2. **新增或修改的文件**：`src/quant_system/performance/analyzer.py`、`src/quant_system/visualization/plots.py`、`main.py`。
3. **已实现的功能**：总收益、自然日年化收益、年化波动率、最大回撤、夏普、胜率、平均盈利/平均亏损盈亏比、交易次数、平均持仓时间；入口生成四类 PNG 和账户快照。
4. **运行过的命令和测试结果**：`main.py` synthetic/test 演示成功，生成 metrics、quality、orders、snapshots 和四类图表。
5. **核心数据结构、算法和公式**：回撤为 `equity/equity.cummax()-1`；夏普为超额日收益均值除以日标准差再乘 `sqrt(252)`。
6. **采用该方案的原因**：指标直接基于每日账户净值和已完成 FIFO 交易，避免只看收盘价格收益。
7. **可选替代方案**：可接入 empyrical、QuantStats 或风险归因框架。
8. **性能瓶颈和后续优化方向**：图表逐次生成；报告数量增加时可统一报告编排和模板化。
9. **面试官可能追问的问题及回答思路**：为什么无完整盈利和亏损时盈亏比为空？因为分母或样本不存在，返回空值比伪造 0 更准确。
10. **尚未完成的内容**：基准当前使用输入股票价格归一化演示，尚未接入独立指数数据。
11. **下一阶段开始前需要确认的事项**：确认测试覆盖和 README 验收要求。
