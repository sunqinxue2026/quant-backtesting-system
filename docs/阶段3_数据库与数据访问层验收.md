## 5. 核心数据结构、算法和公式

- ORM 模型：使用 SQLAlchemy Declarative Base 和类型化 `Mapped` 字段描述表结构。
- 行情唯一键：`(symbol, trade_date, price_type)`。
- 查询条件：股票代码、开始日期、结束日期和价格口径，结果按 `trade_date ASC` 排序。
- 事务：`with session_factory.begin()` 成功时提交，异常时回滚。
- 金额和价格：使用 `Numeric(18, 6)` 或 `Numeric(18, 2)`；第三阶段不计算收益率和交易费用公式，这些属于后续阶段。

## 6. 采用该方案的原因

SQLAlchemy 2.x 同时支持 MySQL 和 SQLite，模型、约束和事务接口统一，便于先用 SQLite 做快速、可重复的本地测试，再切换到 MySQL。Repository 将查询和写入封装起来，避免入口程序直接依赖 ORM 细节。数据库唯一约束作为最后一道一致性保障，不能只依赖 Python 预检查。

## 7. 可选替代方案

- 使用 Alembic 管理增量迁移，而不是当前的 `create_all` 加初始化说明。
- 使用原生 SQL、`LOAD DATA` 或 `executemany` 提高大批量行情导入速度。
- 使用 SQLModel 简化模型定义。
- 使用专门的 Unit of Work 类统一多个 Repository 的事务提交。

## 8. 性能瓶颈和后续优化方向

当前 `bulk_insert_daily` 会将输入迭代器转换为列表并交给 ORM，适合本阶段的小型和中型批量验证。数据量变大时，需要分块写入、批量 SQL、MySQL `LOAD DATA`、复合索引设计和分区表。当前 `count_daily` 为验证清晰度使用实体查询，后续可改为数据库 `COUNT(*)`。生产环境应使用 Alembic 管理表结构变化，并补充真实 MySQL 的索引执行计划验证。

## 9. 面试官可能追问的问题及回答思路

**为什么行情表要把 price_type 放进唯一约束？**

不同复权口径下同一股票同一天的价格可能不同。把价格口径纳入唯一键，可以同时保存不同研究口径，避免后写数据覆盖先写数据。

**为什么自动化测试用 SQLite？**

SQLite 不需要额外服务，适合快速验证模型、约束、查询和事务；真实 MySQL 则通过 Navicat Premium 17 连接本机实例进行集成核验。两者结合可以同时获得快速自动化测试和真实数据库行为验证。SQLite 不能完全替代 MySQL，因此本阶段额外记录了 MySQL 8.0.37 的实测结果。

**为什么不能只在 Python 中检查重复？**

并发写入或不同进程同时导入时，应用层检查存在竞态。数据库唯一约束可以在存储层最终保证一致性。

**事务失败时如何保证整批行情不残留？**

批量写入放在 `session.begin()` 事务中；其中一条触发唯一约束异常，事务整体回滚，测试验证数据库中最终为零条。

### 5. 核心数据结构、算法和公式
ImportResult 包含 batch_id、inserted_rows、CleanResult。流程为 load → clean → with factory.begin() → 创建批次 → 插入行情 → commit。日期使用 date.fromisoformat；数值通过 Decimal(str(value)) 转换，并按价格6位、成交量/额4位 ROUND_HALF_EVEN 量化。成功时 inserted_rows=accepted_rows；批次 units_json 的 _metadata 和 _quality_report 保存追溯信息。CSV原始摘要可追溯文件，但不证明行情真实性。

### 6. 采用该方案的原因
复用已有适配器、清洗器和 Repository，保持层次独立；事务包住批次与行情，避免半批写入；不覆盖冲突行情，避免研究输入被悄悄改变。沿用现有 JSON 字段避免对现有 MySQL 表做隐式结构升级。

### 7. 可选替代方案
可采用显式幂等键跳过已导入文件、人工确认后 upsert、独立元数据/质量报告表，或使用 Alembic 增加字段；本次不引入这些额外规则。

### 8. 性能瓶颈和后续优化方向
当前 CSV 和清洗结果驻留内存，ORM 对象整批构建；大文件可分块清洗、批量 SQL 写入，但仍需明确整批原子性。单位仅记录不换算。DB提交与报告文件写出非原子，报告失败需按已输出批次ID查询，不能直接重跑。

### 9. 面试官可能追问的问题及回答思路
为什么批次和行情同事务？避免出现有批次无完整行情的失败残留（零 accepted 的正常质量批次除外）。为什么不覆盖重复？保证已入库研究数据稳定，冲突显式暴露。如何证明回滚？测试先插入新键再遇到旧键冲突，确认新键和新批次均不存在，旧数据保持两条。SQLite通过是否等于MySQL通过？不是。新脚本另有真实MySQL手动验证记录；MySQL自动化集成测试仍未实现。
