# 开发计划与协作规范

更新日期：2026-11-13。

## 角色与目标

用户为项目负责人和学习者，准备国内初级量化开发工程师岗位；开发助手负责实现、工程完整性、代码质量、测试与代码讲解。交流使用中文；代码标识符与技术术语采用规范英文。

## 当前基线

第一至第八阶段及整体研究演示版已由用户在对话中确认验收通过。当前不自动开展新功能。历史范围和证据保留于各阶段验收报告；本文件不替代原始报告。

## 每次开发任务的执行顺序

1. 说明任务目标、范围与预期结果。
2. 理解现有结构，检查相关源码、依赖、测试和调用方。
3. 列明准备修改的文件，解释方案及兼容影响。
4. 重要技术决策先说明方案和理由，等待负责人确认；不确定业务规则先确认。
5. 只修改相关代码，不随意重写正常模块或破坏接口。
6. 运行与变更相匹配的测试；核心逻辑必须有测试。公共接口变化必须检查调用方。
7. 分析真实结果；先定位失败原因，不通过删除断言或绕过测试掩盖问题。
8. 汇报修改、验证命令与结果、未完成事项和适用边界。
9. 同步进度；重要决策写入 TECHNICAL_DECISIONS.md，学习内容写入 INTERVIEW_NOTES.md。

## 质量约束

- 不以伪代码、空函数或 TODO 充当完成实现；不编造测试、性能或执行结果。
- 不擅自删除文件。数据库结构变更前说明迁移、旧数据兼容及回退影响；create_all 不能充当已有表升级工具。
- 不确定第三方 API 时先确认项目实际安装版本及官方文档。
- 不为赶进度跳过必要验证；未经验证的部分明确标注。
- 源文件变化涉及派生报告或文档时，同步更新或明确指出未同步内容。
- Git 提交遵循实际授权范围，不提交凭据、数据库、虚拟环境、缓存或生成报告。

## 重要实现后的学习说明

围绕真实文件、函数和测试说明设计理由、解决的问题、数据结构与算法、时间和空间复杂度及假设、替代方案、面试追问与结合代码的回答。未做性能基准时只讨论分析复杂度，不报告实测吞吐量。
